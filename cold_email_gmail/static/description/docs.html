Cold Email for Gmail

Schedule one-off emails and send them through Gmail entirely over its REST API — no SMTP, no password, no app-specific password.

00 What it is

Every Gmail operation is an HTTPS call to gmail.googleapis.com. The module never touches ir.mail_server, mail.mail or fetchmail.server, and it does not depend on Odoo's google_gmail addon.

That addon is worth a word, because it looks like the obvious thing to build on. It uses OAuth only to mint a bearer token, then hands that token to SMTP as an XOAUTH2 password: 

# addons/google_gmail/models/ir_mail_server.py
connection.docmd('AUTH', f'XOAUTH2 {oauth_param}')

Its default scope is https://mail.google.com/ — the SMTP/IMAP scope, not an API scope. Building on it would also mean inheriting a hardcoded redirect URI, an admin-only connect button that breaks per-user mailboxes, and Enterprise-only IAP branches. So this module brings its own OAuth flow, controller, token store and API client.

It does reuse generic core mail infrastructure — chatter (mail.thread), activities and mail.render.mixin for placeholders — because none of that has anything to do with the SMTP connector.

01 Google Cloud setup

Nothing works until an OAuth client exists. Do this before installing.

  1. Create a project at console.cloud.google.com.
  2. APIs & Services → Library → enable the Gmail API.
  3. OAuth consent screen. Choose Internal if every sender is on your Google Workspace domain — no review needed and refresh tokens are long-lived. Otherwise External, and add each sender under Test users.
  4. Credentials → Create credentials → OAuth client ID → Web application.
  5. Add the authorised redirect URI, exactly: 
    https://your-odoo-domain.com/cold_email/oauth/callback
    The Settings page prints the exact string for your instance — copy it from there rather than typing it.
  6. Paste the Client ID and Client Secret into Settings → Cold Email.
Testing mode expires tokens after 7 days

While the consent screen sits in Testing, Google expires refresh tokens weekly. The mailbox flips to Authorisation Expired and Reconnect fixes it. This is Google's behaviour, not a defect — only an Internal app or a published, verified app gets long-lived tokens.

The module requests two scopes and no more:

ScopeTierNeeded for
gmail.sendSensitiveSending — users.messages.send
gmail.readonlyRestrictedReading back the real Message-ID, bounce detection, capturing the connected address

Using users.getProfile instead of Google's oauth2/v2/userinfo means no userinfo.email scope is needed — one fewer line on the consent screen.

02 Install

./odoo-bin -c <conf> -d <db> -i cold_email_gmail

Then grant a role under Settings → Users → Cold Email.

GroupCan do
UserConnect their own mailbox, schedule and manage their own emails, use templates and tags
ManagerAll of the above, plus every mailbox and email in the company, and delete rights

Then open Settings → Cold Email and paste the Client ID and Client Secret from step 01. The page also shows the exact redirect URI to register in the Google Cloud console.

03 Connect a mailbox

Cold Email → Configuration → Mailboxes → New. Name it, save, then press Connect Gmail. A rep can only connect a mailbox that belongs to them; a manager can connect anyone's.

Connect Gmail │ auth URL built under sudo(): scopes, PKCE challenge, │ state = { mailbox id + HMAC signature } ▼ accounts.google.com — user grants gmail.send + gmail.readonly │ ?code=…&state=… ▼ /cold_email/oauth/callback verify state → consteq(HMAC) → 403 if forged ▼ POST oauth2.googleapis.com/token authorization_code + PKCE verifier ▼ GET gmail/v1/users/me/profile ← the address that ACTUALLY authenticated ▼ state = connected

The Gmail Address field is filled in by Google, not by whatever was typed into Odoo, and the same address cannot be connected twice in one company. Press Send Test Email to prove the whole chain in one click — it sends a short message to your own user's address. Reconnect repeats the consent flow and Disconnect revokes the token at Google and forgets it locally.

04 Templates and tags

Cold Email → Configuration → Email Templates holds reusable content: a name, a subject and an HTML body. Picking a template on an email copies its subject and body across. Nothing links back afterwards, so editing a template never touches emails that are already scheduled.

Tags (Configuration → Tags) are free-form coloured labels for grouping emails, for example “Canada Drip 5”. They have no effect on sending.

Personalising with placeholders

Each email has a Name and a Company Name field. Type / in the Subject or Body to insert them as dynamic placeholders. They are rendered at send time, against the email itself:

WhereSyntaxExample
Subject{{ object.field }}Quick question about {{ object.company_name }}
Body<t t-out="object.field"/>Hi <t t-out="object.name"/>,

Once an email is sent, its subject and body are replaced with what actually went out, so the record shows the real text instead of the raw placeholders.

05 Schedule an email

Cold Email → Emails → New. Each email is one row in a flat list, and that list is also the sending queue.

  1. Pick Send From — only connected mailboxes are offered.
  2. Fill in To, and optionally Name, Company Name and Tags.
  3. Pick a Template or write the Subject and Body directly.
  4. Set Schedule Date & Time. It defaults to now.
  5. Save. The email stays Scheduled until the next cron beat finds it due.
scheduled sent bounced failed cancelled

Cancel stops a scheduled email (a sent one cannot be cancelled). Retry puts a failed or cancelled one back in the queue. Every email has chatter, so you can log notes and schedule follow-up activities per recipient. Use the Due Now, Failed and Bounced filters to see what needs attention.

Bounce protection

If an address bounced before, on any mailbox, the form warns you as soon as you type it, and the email is cancelled at send time to protect your sender reputation. The check ignores letter case.

06 Replies and threading

An email is either a New Thread or a Reply. To follow up, open a sent email and press Reply. That creates a new email with Reply To, the mailbox, the recipient and a Re: subject already filled in.

NEW THREAD MIME Subject: Quick question about Acme POST /messages/send { raw } ← no threadId ▼ Gmail creates thread T1 ▼ Gmail REWRITES the Message-ID we generated GET /messages/{id}?format=metadata&metadataHeaders=Message-Id └─> gmail_thread_id = "T1" rfc_message_id = "<abc@mail.gmail.com>" REPLY (parent_id = the sent email above) MIME Subject: Re: Quick question about Acme ← prefix added In-Reply-To: <abc@mail.gmail.com> References: <abc@mail.gmail.com> POST /messages/send { raw, threadId: "T1" } ▼ lands in the SAME conversation

Two things that bite people:

  1. Gmail overwrites Message-ID on send. The ID needed for the next In-Reply-To can only be obtained by reading the message back with messages.get. That is why gmail.readonly is in the scope list.
  2. threadId alone does not thread. Gmail files a message into a thread only when the threadId, the References/In-Reply-To headers and the subject all agree. The module always sets the three together.
Rules the module enforces

A reply must point at an email that is already sent, from the same mailbox — Gmail can only continue a conversation from the account that holds it. A reply whose parent has no thread or Message-ID yet automatically degrades to a new thread instead of mis-threading.

— Crons and queue

Send queued messages — every 5 minutes

for each connected mailbox: ├─ daily quota spent ? ──> skip mailbox └─ for each due email, oldest first (up to the remaining quota): ├─ outside the sending window ? ──> leave it ├─ min_delay_seconds not elapsed ? ──> stop, wait for the next beat ├─ mailbox not connected / no recipient / empty subject or body │ / address bounced before ──> cancelled, with the reason ├─ render subject and body, build MIME (multipart text + HTML) ├─ POST /messages/send (with threadId when replying) ├─ GET /messages/{id} → the real Message-ID └─ store ids, freeze the rendered text, count it against the quota

One cron run sends at most 200 messages across all mailboxes. The daily counter rolls over at midnight in each mailbox's own timezone. Each send is committed on its own, so a crash cannot lose track of what already went out.

Detect bounces — every 15 minutes

One API call covers a whole mailbox instead of polling each thread:

GET /messages?q=-from:me newer_than:7d&labelIds=INBOX → collect threadIds → match sent emails by gmail_thread_id in one query → sender is mailer-daemon@ / postmaster@ ? state = bounced

Clean up — weekly

Deletes sent, bounced and cancelled emails older than 12 months. Scheduled and failed emails are never collected.

— Bounces

When a bounce notice from mailer-daemon@ or postmaster@ lands in the inbox thread of a sent email, that email becomes Bounced. From then on any new email to the same address, from any mailbox, is cancelled at send time with a pointer to the original bounce. The module detects bounces only; it does not detect human replies.

— Error handling

ConditionBehaviour
401Refresh the token and replay the request once
429, 5xx, rate-limit or backend-error reasonsTransient: retry in 2n minutes (n = attempt, capped at 120), give up after 5 attempts
domainPolicy, failedPrecondition, forbidden, insufficientPermissionsMailbox problem: stop this mailbox's batch, leave its queue untouched, set state = error
OAuth invalid_grantAuthorisation revoked or expired: state = expired, queue untouched
Other OAuth errors (e.g. invalid_client)Bad Client ID/Secret: state = error, queue untouched
Any other 4xxThis message is bad: state = failed with the error text

A mailbox-level failure never fails the messages. A settings typo would otherwise burn the whole queue and hammer Google's token endpoint once per email. Bad mailboxes are skipped; healthy ones in the same run keep sending. Each send runs inside a cr.savepoint(), so one bad row cannot roll back the batch.

The Response tab of a sent or failed email shows the outcome, the Gmail identifiers, the HTTP status and reason of a failure, and Google's raw response.

— Security

  • OAuth credentials (refresh_token, access_token, access_token_expiration, pkce_verifier) live on groups='base.group_system' fields and appear in no view. A Cold Email User cannot read them; all sending goes through sudo().
  • The OAuth callback verifies an HMAC-signed state; a forged one gets a 403.
  • PKCE (S256) is used on the authorisation-code exchange.
  • Record rules: users see only their own mailboxes and emails; managers see the whole company.
  • Mailboxes, emails, templates and tags can be created and edited by users; only managers can delete.

— Compliance

gmail.send is a sensitive scope; gmail.readonly is a restricted one.

  • Internal Workspace app: neither needs Google review.
  • Public or multi-customer product: Google requires OAuth verification and a third-party CASA security assessment for the restricted scope. Budget for it early.
No unsubscribe link is added

The module does not add an unsubscribe footer or a List-Unsubscribe header; that mechanism was deliberately dropped. If your outreach needs an opt-out, put it in the body yourself, and respect the laws that apply to your recipients.

Keep the caps honest. Gmail's sending limits are separate from API quota, and rotating mailboxes to exceed them violates Google's terms.

— Limitations

Not included: campaigns and multi-step sequences, contact lists, open/click tracking, A/B testing, reply detection, unsubscribe handling, Pub/Sub push notifications (the 15-minute poll is sufficient at this scale) and multi-company record rules (company_id is already on the models, so the rules are a one-file addition).

Delivery is at-least-once, not exactly-once

Between “Gmail accepted the message” and “we recorded it” there is a window of a few ORM writes. If one failed, the savepoint would roll back and the next cron run would re-send. The risky messages.get call is already guarded, so the remaining window is very small.
