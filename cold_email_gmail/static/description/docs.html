Cold Email for Gmail

Multi-step cold outreach that talks to Gmail entirely over its REST API — no SMTP, no password, no app-specific password.

00 What it is

Every Gmail operation is an HTTPS call to gmail.googleapis.com. The module never touches ir.mail_server, mail.mail or fetchmail.server, and it does not depend on Odoo's google_gmail addon.

That addon is worth a word, because it looks like the obvious thing to build on. It uses OAuth only to mint a bearer token, then hands that token to SMTP as an XOAUTH2 password: 

# addons/google_gmail/models/ir_mail_server.py
connection.docmd('AUTH', f'XOAUTH2 {oauth_param}')

Its default scope is https://mail.google.com/ — the SMTP/IMAP scope, not an API scope. Building on it would also mean inheriting a hardcoded redirect URI, an admin-only connect button that breaks per-user mailboxes, and Enterprise-only IAP branches. So this module brings its own OAuth flow, controller, token store and API client.

It does reuse generic core mail infrastructure — mail.blacklist, the mail.thread.blacklist mixin, mail.render.mixin — because none of that has anything to do with the SMTP connector.

01 Google Cloud setup

Nothing works until an OAuth client exists. Do this before installing.

  1. Create a project at console.cloud.google.com.
  2. APIs & Services → Library → enable the Gmail API.
  3. OAuth consent screen. Choose Internal if every sender is on your Google Workspace domain — no review needed and refresh tokens are long-lived. Otherwise External, and add each sender under Test users.
  4. Credentials → Create credentials → OAuth client ID → Web application.
  5. Add the authorised redirect URI, exactly: 
    https://your-odoo-domain.com/cold_email/oauth/callback
    The Settings page prints the exact string for your instance — copy it from there rather than typing it.
  6. Paste the Client ID and Client Secret into Settings → Cold Email.
Testing mode expires tokens after 7 days

While the consent screen sits in Testing, Google expires refresh tokens weekly. The mailbox flips to Authorisation Expired and Reconnect fixes it. This is Google's behaviour, not a defect — only an Internal app or a published, verified app gets long-lived tokens.

The module requests two scopes and no more:

ScopeTierNeeded for
gmail.sendSensitiveSending — users.messages.send
gmail.readonlyRestrictedReading back the real Message-ID, reply detection, capturing the connected address

Using users.getProfile instead of Google's oauth2/v2/userinfo means no userinfo.email scope is needed — one fewer line on the consent screen.

03 Connect a mailbox

Cold Email → Configuration → Mailboxes → New. Name it, save, then press Connect Gmail.

Connect Gmail │ auth URL built under sudo(): scopes, PKCE challenge, │ state = { mailbox id + HMAC signature } ▼ accounts.google.com — user grants gmail.send + gmail.readonly │ ?code=…&state=… ▼ /cold_email/oauth/callback verify state → consteq(HMAC) → 403 if forged ▼ POST oauth2.googleapis.com/token authorization_code + PKCE verifier ▼ GET gmail/v1/users/me/profile ← the address that ACTUALLY authenticated ▼ state = connected

The Gmail Address field is filled in by Google, not by whatever was typed into Odoo. Press Send Test Email to prove the whole chain in one click.

04 Build a list

Cold Email → Contacts. Import with the standard Odoo CSV importer — nothing custom. Prospects stay in cold.contact rather than res.partner on purpose: cold lists are bulk-imported, unverified and often discarded, and they should not silently become part of the company's real contact database. Create Contact promotes a warm reply into a real partner.

Inheriting mail.thread.blacklist brings email_normalized, a searchable is_blacklisted, the message_bounce counter and chatter at no cost — that is the entire suppression layer.

05 Run a campaign

Cold Email → Campaigns → New. Pick a connected mailbox, write the steps, add contacts, press Start.

Q3 SaaS Outreach mailbox: sales@acme.com ├── step 1 +0d new_thread "Quick question about {{ object.company_name }}" ├── step 2 +3d reply "Following up" ├── step 3 +4d reply "Last note" └── step 4 +7d new_thread "Different angle"

Delays count from the previous step, not from day zero, so reordering or inserting a step does not silently shift everything after it.

draft running paused done cancelled
Pause loses nothing

Pausing does not delete queued rows. The cron skips campaigns that are not running, so resuming costs nothing and re-enqueues nothing. Adding contacts to an already-running campaign starts them immediately; blacklisted and already-enrolled contacts are skipped, and the wizard says how many and why before you commit.

— Threading: new conversation vs. reply

Each step either opens a new conversation or continues the existing one. This is the part of the Gmail API with a trap in it — two, in fact.

Step 1 · day 0new_thread
Subject: Quick question about Acme To: jane@acme.com (no In-Reply-To, no References) POST /messages/send { raw } ← no threadId

Gmail creates thread T1 — and rewrites the Message-ID we generated. The module reads the real one back with GET /messages/{id}?format=metadata&metadataHeaders=Message-Id and stores gmail_thread_id = T1, last_rfc_message_id = <abc@mail.gmail.com>.

Step 2 · day 3reply
Subject: Re: Quick question about Acme ← prefix required In-Reply-To: <abc@mail.gmail.com> References: <abc@mail.gmail.com> POST /messages/send { raw, threadId: "T1" }

Lands in the same conversation. The chain advances to this message's ID.

Step 4 · day 14new_thread
Subject: Different angle (chain deliberately reset)

A mid-sequence new_thread step starts a fresh conversation and becomes the new anchor for any later reply steps.

Trap 1 · Gmail overwrites Message-ID on send

Whatever you put in the MIME is not what the recipient's client sees. The ID needed for the next follow-up's In-Reply-To can only be obtained by reading the message back with messages.get. That single requirement is why gmail.readonly is in the scope list — it is not only for reply detection.

Trap 2 · threadId alone does not thread

Gmail attaches a message to a thread only when the threadId, the References/In-Reply-To headers and the subject line all agree. Set one without the others and it silently starts a new conversation. The module always writes the three together, as a unit.

A reply step with no thread to reply into — the first step, or one whose predecessor never went out — degrades to new_thread rather than mis-threading.

— Data model

res.users ──1:N──> cold.mailbox ──1:N──> cold.campaign │ │ │ ├──1:N──> cold.sequence.step │ │ │ └──1:N──> cold.enrollment <──N:1── cold.contact │ │ └─────────────────────────────────────┴──1:N──> cold.mail
ModelRole
cold.mailboxOne connected Gmail account. Owns the OAuth tokens and the sending policy.
cold.contactA prospect on the cold list, kept out of res.partner on purpose.
cold.campaignA mailbox, an ordered sequence, and the enrolled contacts.
cold.sequence.stepOne message: its copy, its delay, and how it threads.
cold.enrollmentOne contact's run through one campaign. Holds the Gmail thread state.
cold.mailOne outgoing email. This is also the queue.

Two shapes are worth explaining. cold.enrollment exists because the same contact can sit in several campaigns at once, each with its own Gmail conversation — the thread state has to live somewhere per-pairing. And there is deliberately no queue model: a cold.mail row in state scheduled with a future scheduled_at is a queued job, so there is nothing to keep in sync.

— Crons and the queue

CronEveryDoes
_cron_send_queued5 minSends everything due, mailbox by mailbox
_cron_sync_replies15 minDetects replies and bounces, stops those sequences
_cron_gc1 weekDrops sent/cancelled rows older than 12 months
for each connected mailbox: ├─ outside its window ? ──> skip mailbox ├─ daily quota spent ? ──> skip mailbox └─ for each due cold.mail, oldest first: ├─ blacklisted / campaign not running ──> cancelled ├─ render copy, build MIME (+ unsubscribe link and header) ├─ POST /messages/send (threadId only when replying) ├─ GET /messages/{id} → the real Message-ID ├─ store ids, update the enrollment's thread state └─ CREATE the next step's cold.mail ← how sequences advance

Follow-ups are queued lazily — the next email is created only after the current one actually sends. Nothing is pre-scheduled days ahead, so a pause or a reply never leaves stale rows behind. Each send is isolated in a cr.savepoint(), so one bad row cannot roll back the batch.

Rate control lives entirely in the loop guard: the per-mailbox daily limit, the minimum delay between two sends, and the window check in the mailbox's own timezone. A mailbox that is pacing simply waits for the next cron beat rather than blocking the worker.

— Replies, bounces, unsubscribes

Reply detection costs one API call per mailbox, not one per conversation:

GET /messages?q=-from:me newer_than:7d&labelIds=INBOX → collect threadIds → match cold.enrollment.gmail_thread_id in one query → sender is mailer-daemon@ / postmaster@ ? bounced : replied → cancel that enrollment's remaining scheduled emails

Two hard bounces add the address to mail.blacklist automatically.

Unsubscribe

Every message carries a visible footer link and a List-Unsubscribe header with List-Unsubscribe-Post: List-Unsubscribe=One-Click — both required by Google's bulk-sender rules. The route is public and HMAC-signed:

/cold_email/unsubscribe/<contact_id>/<token> 403 on a forged token → mail.blacklist._add(email) ← GLOBAL, every future campaign → enrollments still running → unsubscribed → their pending cold.mail rows → cancelled

An enrollment that already reached done keeps that state. The unsubscribe stops what is running; it does not rewrite the history of a sequence that already finished. The address is suppressed either way.

pending running replied bounced unsubscribed done cancelled

— Error handling

ConditionBehaviour
401Refresh the token and replay the request once
429, 403 rateLimitExceeded, 5xxTransient — retry in 2n minutes, capped at 120, give up after 5
403 domainPolicy / failedPreconditionMailbox problem — stop this mailbox's batch, queue untouched, state = error
OAuth invalid_grantAuthorisation revoked or expired — state = expired, queue untouched
OAuth invalid_clientBad Client ID/Secret — state = error, queue untouched
Any other 4xxThis message is bad — state = failed with the error text
A mailbox failure never fails the messages

A settings typo would otherwise burn an entire campaign and hammer Google's token endpoint once per queued email. Broken mailboxes are skipped with their queue intact and the reason recorded on the mailbox; healthy mailboxes in the same cron run keep sending.

One implementation note for anyone editing this code: the savepoint's rollback calls cr.clear(), so anything written inside it is discarded. That is why mailbox diagnostics are returned to the caller and written outside the savepoint — writing them in place looks correct and silently loses them.

— Security

  • OAuth credentials — refresh_token, access_token, access_token_expiration, pkce_verifier — live on groups="base.group_system" fields and appear in no view. A Cold Email User genuinely cannot read them, even for their own mailbox; all sending goes through sudo().
  • The API client redacts the Authorization header before any debug logging. Tokens are never written to the log.
  • The OAuth callback verifies an HMAC-signed state; a forged one gets a 403. PKCE (S256) is used on the code exchange.
  • Record rules scope mailboxes and campaigns to their owner, and enrollments and emails to their campaign. Managers see the whole company. The cold list itself is shared across the group — it is team property.
  • _get_unsubscribe_token and _get_access_token are private and unreachable over RPC.

— Compliance

gmail.send is a sensitive scope; gmail.readonly is a restricted one.

DeploymentWhat Google requires
Internal Workspace appNothing. No review.
Public / multi-customer productOAuth verification and a third-party CASA security assessment for the restricted scope.

Budget for the assessment early rather than treating it as a launch-day task. If you later want the module to label threads inside Gmail, swap gmail.readonly for gmail.modify — same restricted tier, so no extra review burden.

Keep the caps honest. Gmail's sending limits are a separate ceiling from API quota, and rotating mailboxes to get around them violates Google's terms.

— Limitations

Not included in v1: open/click tracking, A/B testing, Pub/Sub push notifications (the 15-minute poll is sufficient at this scale), an analytics dashboard beyond the campaign counters, multi-company record rules (company_id is already on the models, so the rules are a one-file addition), and automatic lead creation on reply. There is also no crm.lead link — a Many2one to it would make crm a hard dependency of the whole module; a bridge module can add it.

Delivery is at-least-once, not exactly-once

Between “Gmail accepted the message” and “we recorded it” there is a window of a few ORM writes. If one failed, the savepoint would roll back and the next cron run would re-send. The risky messages.get call is already guarded, so the remaining window is very small — but closing it completely means committing mid-savepoint, which is a larger structural change than this module warrants.
